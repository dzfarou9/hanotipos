Security & Cost Audit · 2 September 2026

Hanoti POS — Full-App Audit

Target: hanoti-farou9 · Flutter (Android + Web) · Firebase Auth / Firestore / Remote Config
Method: four parallel domain audits — security rules & configs, auth flows, subscription & billing, data storage & PII

Tenant isolation in the Firestore rules is solid — no cross-tenant read or write was found. The real exposure is on the money and credential side: the paywall and trial system are client-suggestions rather than server-enforced, and the QR login ships the user's actual password under a key baked into every APK. Three findings are rated critical; the bill-risk ceiling is set by two silent read-amplification paths and unenforced App Check.

Critical

CriticalC-1

QR login embeds the real phone + password, encrypted with a key baked into every APK

lib/config/qr_login_config.dart:10lib/services/qr_login_service.dart:30-57lib/screens/settings_screen.dart:889-896lib/screens/login_qr_scan_screen.dart:111-128
What's wrong
The QR payload is AES-256-CBC of {phone, password} under a compile-time constant key. There is no server, no nonce, no one-time use — the QR is the credential, and the 90-second expiry is checked only against the scanning device's clock.
Attack
Decompile the public APK once, extract the key, then decrypt any QR ever photographed or screenshotted — a store owner's screen from across the room — and you hold their permanent password, not a session. The app's own "scan QR from gallery" path means a stolen screenshot works directly, no key extraction needed. Because no password-change or reset path exists (H-3), a leaked QR is an unfixable breach.
Fix
Replace with a server-mediated one-time exchange: a Cloud Function mints a 60–120 s single-use opaque token bound to the uid; the scanning device redeems it for a Firebase custom token. The password must never enter a QR, and no secret may be shared across installs.
CriticalC-2

The paywall trusts local storage first — free access forever, even while online

lib/services/firebase_service.dart:1692-1705lib/services/database_service.dart:317-337lib/screens/splash_screen.dart:145-168
What's wrong
isSubscriptionActive() returns true whenever the local Hive end_date is in the future, without contacting Firestore. The online check runs only when local state is expired or missing — and its timeout and error paths fall back to the local verdict. The cached value is unsigned and has no re-verification deadline.
Attack
On web, no root is needed: DevTools → IndexedDB → set subscription_end_date to 2999-12-31 → reload. Full app access forever, with Firebase working fine. On rooted Android, edit the Hive box file. Every user who learns the trick is 100% revenue loss.
Fix
Server-first with a capped lease: store last_verified_at, treat local state as offline grace for ≤ 24–48 h after a successful server confirmation, and on web never trust end_date past one session.
CriticalC-3

Trials are self-serviceable for a year — and a self-issued trial overrides a paid subscription

firestore.rules:39-48firestore.rules:104-119lib/services/firebase_service.dart:429-441lib/services/firebase_service.dart:1733-1744
What's wrong
The rules cap a client-created trial at 366 days — matching the code's Remote-Config clamp, not the 7-day business trial. Registration is open (no phone/email verification, H-4) and logout wipes local trial state, so each new account is a fresh trial. Worse, the client picks the maximum end_date across all active subscriptions, so a self-written year-trial at subscriptions/{uid} also wins over a legitimate paid subscription stored at a random doc id.
Attack
Register any phone, then write subscriptions/{uid} with end_date = now + 365d directly via the Firestore API — no app needed. Rules accept it. Perpetual free access, and paying customers can be out-gated by their own trial doc.
Fix
Move trial issuance to a Cloud Function (Auth onCreate) and set allow create: if false for clients; or tighten the rule cap to +8 days. Make the subscription reader treat self-created docs as non-authoritative. Enforce App Check (M-2) so scripted clients can't reach the API at all.

HighH-1

Sync can upload one account's business data into another account

lib/services/sync_service.dart:223-245lib/services/auth_service.dart:295-317lib/services/database_service.dart:282-315lib/services/firebase_service.dart:781,827,1256,1332,1542,1640
What's wrong
syncNow() checks that Hive has a user id and Firebase has a session — never that they are the same uid — and every push stamps the current Firebase uid onto documents. Logout wipes Hive non-atomically before sign-out; a mid-wipe failure leaves user A's unsynced sales on the device, and the next login as user B pushes them into B's Firestore account, customer names and phones included.
Fix
Hard-fail sync when currentUser.uid != stored user_id; make logout step-independent (always attempt sign-out; verify all boxes empty before proceeding); on login, purge business boxes when a foreign owner is detected.
HighH-2

Phone-number enumeration — reachable without the app

lib/services/firebase_service.dart:102-105,239-240assets/translations/en.json:522,527
What's wrong
Login distinguishes "user not found" from "wrong password"; registration reveals "this number is already registered". Because auth is plain email/password, this is testable against the public Firebase Identity Toolkit REST API with the public web API key — client-side limits don't apply to that channel.
Impact
A script can enumerate which phone numbers hold Hanoti merchant accounts — a ready-made phishing target list.
Fix
One generic "invalid phone or password" message; normalize registration errors; enable App Check enforcement and Identity Platform sign-in quotas in the console.
HighH-3

No password reset and no password change — a forgotten password destroys the account

lib/screens/login_screen.dart:546-548lib/services/firebase_service.dart:84,220
What's wrong
The forgot-password button is a no-op, and even if wired up, the synthetic email phone@hanoti.pos is unroutable — reset emails go nowhere. There is no in-app password change, and QR generation requires the password, so a locked-out owner has no path back to their store data. This also makes C-1 leaks permanent.
Fix
Implement in-app password change now (re-authenticate + updatePassword); long-term, add SMS OTP so real resets exist.
HighH-4

No phone-ownership verification — account squatting

lib/services/firebase_service.dart:195-318lib/screens/register_screen.dart:514-515,555-560
What's wrong
"Phone + password" is really "username + password": anyone can register any number without proving they own it, and the format isn't normalized (0551234567 and 551234567 are two different accounts). A squatter who grabs a merchant's number first leaves the real owner facing "already registered" with no recovery path (H-3).
Fix
Verify phone ownership via SMS OTP before account creation; normalize the phone format before building the synthetic email.
HighH-5

Cloud sale deletion can never succeed — the rules reject the query

lib/services/firebase_service.dart:1494-1497firestore.rules:100-101
What's wrong
deleteSale queries sale_items by sale_id with no user_id filter. Firestore rules are not filters: a list query whose constraints don't guarantee permitted results is rejected wholesale, so every sale deletion fails with permission-denied and deleted sales resurface on the next pull.
Fix
Add .where('user_id', isEqualTo: userId) — mirroring _getSaleItemsBatched at firebase_service.dart:682-687, which already does it correctly.
HighH-6

Two silent read-amplification paths can multiply the Firestore bill

lib/services/sync_service.dart:323-360lib/services/firebase_service.dart:548-567,614-633,1422-1441
What's wrong
(a) syncAfterLogin can run up to four full pulls per login (three retries plus a "direct pull" safety net); a full store is ~2,500+ doc reads per pull, so one bad login ≈ 10,000 reads. (b) If the composite indexes aren't deployed, every incremental pull silently falls back to a 500-doc full pull — at the 30-minute cooldown that's a ceiling of ~120k reads/day/user, with no alert.
Fix
Verify the composite indexes from firestore.indexes.json are deployed; distinguish failed-precondition (missing index) from transient errors instead of full-pulling; cap login retries. Set a usage budget alert in the Firebase console.

MediumM-2

App Check is activated with the debug provider; enforcement unverified

lib/main.dart:54-58
What's wrong
activate() is called with no androidProvider or webRecaptchaSiteKey — Android gets the debug provider, web gets nothing. Combined with open signup and no field validation in the rules, a scripted client can write unbounded documents (a direct billing attack).
Fix
Pass Play Integrity (Android) and a reCAPTCHA v3 key (web); then turn on enforcement — not just monitoring — for Firestore and Identity Toolkit in the console.

MediumM-5

Rate limiting is client-side only — and auth failures are retried 4×

lib/helpers/login_rate_limiter.dartlib/services/network_service.dart:78-119
What's wrong
The 5-attempt limiter lives in widget State: it resets on restart, screen re-entry, and reinstall, and the QR login path has none. Worse, NetworkService retries unrecognized FirebaseAuthException codes (wrong-password, user-not-found) up to 4× — burning the legitimate user's own throttle budget and quadrupling a brute-force script's request cost.
Fix
Never retry FirebaseAuthException (auth outcomes are deterministic); treat the limiter as UX and rely on Auth throttling + Identity Platform quotas.

firestore.rules:94-96

Firebase console checklist

These can't be verified from the repo — each is a console-side setting that materially changes the risk of the findings above.

  1. App Check enforcement for Firestore and Identity Toolkit — currently monitored-at-best (M-2, C-3).
  2. API key restrictions — Android key: package + SHA-1; web key: HTTP referrers (M-4).
  3. Auth authorized domains — only domains you actually serve the web app from.
  4. Composite indexes deployed from firestore.indexes.json — otherwise the 120k-reads/day fallback is live (H-6).
  5. Cloud Storage — disable the API (unused) or deploy rules (M-3).
  6. Remote Config — published trial_days = 7; audit who can edit (M-11).
  7. Budget alerts on Firestore reads/writes — the owner's first line of bill defense.
